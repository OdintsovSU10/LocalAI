# ADR-004 — проверка ответа: утверждения, детерминированные проверки, независимый verifier

Статус: принято и реализовано в Stage 07 (`apps/rag-api/src/answer-core/`).

## Контекст

До Stage 07 модель писала ответ свободным текстом. Ссылки [n] она расставляла сама, а правильность чисел, типов значений, редакции и проекта никто не проверял. Prompt Pack требует: ни одно существенное утверждение не попадает в ответ, если verifier не подтвердил его конкретным доказательством. При этом на машине владельца обычно загружена одна локальная модель.

## Решение

- **Черновик вместо текста.** Модель ответа возвращает JSON: атомарные утверждения (`claims`), тип (`amount`, `percentage`, `date`, `period`, `condition`, `comparison`, `fact`) и метки доказательств `E1..En` из пакета Stage 06. Если runtime поддерживает `response_format` с JSON-схемой, она передаётся. Если нет — повтор без схемы. Неразборчивый ответ даёт `system_error` с найденными фрагментами.
- **Детерминированные проверки до модели-verifier и независимо от неё** (`claim-checks.js`, `claim-numbers.js`):
  - метки существуют;
  - доказательство из разрешённого проекта;
  - есть файл или фрагмент для цитаты;
  - каждое число утверждения есть в процитированном доказательстве с той же единицей (процент, дни/месяцы/годы, рубли, дата, доля);
  - тип значения соответствует типу утверждения и его метке («Срок … — 3%» — ошибка);
  - для действующей редакции нельзя опираться только на заменённый пункт, если утверждение не говорит об истории («ранее», «до ДС»).

  Проверки не зависят от модели. Поэтому ложный пропуск verifier-модели не пропускает неверное число, единицу, проект или устаревшую редакцию.
- **Независимый verifier-модель** (`answer-verifier.js`):
  - Целевой режим `separate_model` — другая модель. Маршрут тот же, что у модели ответа, с теми же правами на remote context; `temperature 0`.
  - Изолированный прогон той же модели (`same_model`) — только по явной настройке.
  - Без модели (`separate_model` без имени) или при её сбое ответ проходит только детерминированные проверки. Ответ сообщает об этом: `verification.level = "hard_checks"`, в UI — «Числа и ссылки сверены с документами», а не «Проверено по документам».
  - Пропущенный verifier-ом вердикт считается `ambiguous`, а не `supported`.
- **Ограниченный цикл исправления.** Не больше `answering.maxRepairs` (по умолчанию 1, максимум 2) повторов: поисковые запросы verifier-а в том же scope → доказательства добавляются с новыми метками → черновик пересобирается с причинами отказа → проверка заново. После лимита неподтверждённые утверждения не показываются. Если не осталось ни одного — `insufficient_evidence`.
- **Финальный текст детерминирован** (`answer-renderer.js`):
  - только подтверждённые утверждения со ссылками [n], перенумерованными по показанным источникам;
  - расхождение документов — номерами ссылок;
  - число скрытых утверждений.

  Текст модели вне утверждений (`summary`, заметки verifier-а) пользователю не показывается. Процента уверенности нет.
- **Потоковый режим.** `/api/chat` и `/api/chat/stream` идут по одному конвейеру. Токены черновика не стримятся. Клиент получает статусы `llm_started → verifying_started → (repair_started) → finalizing`, затем финальный текст одним событием `token`.
- **Статусы:** `verified`, `verified_with_conflict`, `insufficient_evidence`, `clarification_required`, `system_error`; `unverified` — только фрагменты при выключенной LLM. Статус и сводка проверки (коды, без текста утверждений) сохраняются с ходом диалога.
- **Флаги:**
  - `answering.verified` (по умолчанию `true`, env `RAG_VERIFIED_ANSWERING`);
  - `verifier.mode` / `verifier.model` (env `RAG_VERIFIER_MODE` / `RAG_VERIFIER_MODEL`).

  Env действует только при чтении и не записывается в `settings.json`. С выключенным флагом ответ API прежний: на этом держится контракт Stage 02.

## Последствия

- Ответ — список проверенных утверждений. Он суше прежнего связного текста, зато каждое утверждение подтверждено.
- На ответ уходит минимум два вызова LLM (черновик и verifier), при исправлении — до шести. Первый токен приходит только после проверки.
- Семантические ошибки без чисел (не та сторона, выдуманное условие) ловит только verifier-модель. Без неё они считаются в `verifier.falsePassRate`, а не скрываются.
- Качество ответа живой модели (`answer.*`) офлайн-eval не измеряет. Его сравнение — на Stage 11 (bakeoff).
